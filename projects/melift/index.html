Walkthrough

The full loop, end to end.

Every surface is built in SwiftUI, themed through a central ColorPalette so the entire app retunes when the user picks Forest, Blue Steel, Light, or Dark. Below: actual captures from the app, and the engineering behind each screen.

01 / 05

Plan the week, not just the workout.

Splits sit above individual workouts. Lifters keep multiple programs — PPL, Upper/Lower, Full Body — and mark one as current so the Log tab always defaults to today’s session in their active rotation.

Engineering: splits and workouts live in separate Postgres tables joined by an ordered split_workouts table; the “current” flag is enforced through a partial unique index so only one split per user can be active at a time.
02 / 05

Build workouts with intent.

Drag exercises into order, set the working set count, and tag each as bilateral or unilateral — with dumbbell-count controls for asymmetric movements. The whole composition is an editable draft until the user saves.

Engineering: a composable form view-model holds an unsaved Workout aggregate with its child workout_exercises; reordering and set changes mutate local state, so a single Save commits the entire tree in one round-trip.
03 / 05

Progress, drawn natively.

Stat tiles, a Weight Moved chart, and a session-by-session history — all rendered with Apple’s Swift Charts. No chart libraries, no WebViews, no JavaScript. The same data powers all three views.

Engineering: a single ProgressService issues window-bounded queries against workout_sessions and aggregates client-side, so the stat tiles, the Weight Moved chart, and the history list share one fetch — no duplicate network hits when the user toggles between Last Week and All Time.
04 / 05

A PR engine, not a leaderboard.

Every completed set is compared against the user’s history across both weight and reps. The detector tags genuine bests in real time, filterable by muscle group, and surfaces them inline next to the set that earned them.

Engineering: the PR routine in ProgressService compares each session’s best sets against historical bests by both load and rep count — so a new 5-rep best at the same weight still counts, not just heavier loads.
05 / 05

A library that ships, plus one you build.

Hundreds of defaulted exercises with muscle-group filters, search, and favorites — layered with user-created exercises that live on the same screen. Workouts and splits compose from either, then export and import via a versioned .melift JSON format.

Engineering: the LibraryViewModel merges defaulted and user-owned exercises through a single Combine pipeline, with favorites kept in their own table so star toggles never invalidate the full exercise list.

Platform integration

The rest timer leaves the app.

Built on ActivityKit and WidgetKit, MeLift’s rest timer continues running on the Lock Screen and inside the Dynamic Island. Lifters don’t have to keep the app foregrounded between sets — the countdown is right there on the home indicator, even one-handed mid-rack.

Implementation

A dedicated RestTimerLiveActivityManager owns the Activity<RestTimerAttributes> lifecycle: start, push state updates as the user re-racks early, and end on completion. The widget extension renders the same model on the Lock Screen, in the compact island, and in the expanded island.

Under the hood

A small, deliberate architecture.

MVVM with a clean services boundary. SwiftUI views never touch Supabase directly — every read and write flows through a typed service that maps a snake_case database row to a domain model the views actually want.

SwiftUI Views declarative · themed · per-feature
↓
ViewModels (Combine) @Published · @MainActor
↓
Services Auth · Workout · Progress · Exercise
↓
Database Models Codable · snake_case ↔ camelCase
↓
Supabase PostgreSQL · Auth · PostgREST
No N+1 queries

Workouts and splits are pulled with a single nested select(...) — workouts(*, workout_exercises(*, exercises(*))) — in one round-trip.

Secure session

Supabase Auth handles JWT lifecycle; the app caches the user profile in Keychain via a KeychainHelper wrapper, never UserDefaults.

Portable workouts

WorkoutShareService serializes splits, workouts, and custom exercises to a versioned JSON payload with a .melift extension so users can share programs offline.

Themable to the core

ThemeManager exposes a single ColorPalette; every view reads through it so switching themes (Forest, Blue Steel, Dark, Light) updates the entire app instantly.

Highlights

What I’d talk about in an interview.

The moments where MeLift went past CRUD — product decisions, performance trade-offs, and platform features that took real engineering to land.

01

PR DETECTION ENGINE

Two-dimensional comparison (load × reps) against full user history, so a new 5-rep best at the same weight still counts. Lives in ProgressService and powers the badge UI in real time.

02

LIVE ACTIVITIES

Full ActivityKit integration for the rest timer on the Lock Screen and Dynamic Island — far past a basic in-app countdown, and a real iOS 16+ platform feature.

03

EFFICIENT QUERIES

Hierarchical Supabase reads (workouts → exercises → sets) consolidated into single nested select calls to eliminate N+1 round-trips on the hot loading paths.

04

PORTABLE FORMAT

Versioned .melift JSON payloads for sharing programs across users and devices, designed to be forward-compatible as the schema evolves.
